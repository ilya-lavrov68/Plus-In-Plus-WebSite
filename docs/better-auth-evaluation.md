# Оценка перехода на Better Auth

Дата: 2026-11-03. Статус: решение-рекомендация, код не менялся.

## 1. Что есть сейчас

Аутентификация собрана на **Auth.js v5** плюс собственный слой:

| Возможность | Где живёт | Объём |
| --- | --- | --- |
| Вход по паролю | `lib/credentials.ts` (bcryptjs, dummy-hash против таймингов) | ~300 строк |
| MFA: TOTP + backup-коды | `lib/mfa.ts`, `lib/pending-login.ts` | ~200 строк |
| Passkeys (WebAuthn) | `lib/credentials.ts`, `lib/webauthn-config.ts` | внутри credentials |
| Refresh-сессии с ротацией и отзывом | `lib/auth-sessions.ts` | ~280 строк |
| Политика сессий, лимит устройств | `lib/session-policy.ts` | константы |
| Rate limit, прогрессивная задержка | `lib/rate-limit.ts` | — |
| Роли и staff-гейты | `lib/admin-session.ts`, `proxy.ts` | — |
| Схема БД | `accounts`, `auth_sessions`, `pending_logins`, `mfa_backup_codes`, `webauthn_credentials` | 5 таблиц |

Всё это покрыто тестами (из 375 тестов примерно пятая часть касается входа, MFA, сессий и ролей).

## 2. Что даёт Better Auth

Проверено по npm и документации на 2026-11-03: версия **1.7.15**, peer-зависимости включают `next ^14 || ^15 || ^16` и `react ^19`, адаптеры — Kysely, Drizzle, Prisma, Mongo; для SQLite/libSQL есть `@libsql/kysely-libsql`.

Закрывает почти весь наш список:

- `emailAndPassword` — вход по паролю, хеширование, смена/сброс пароля;
- плагин **twoFactor** — TOTP, 10 одноразовых backup-кодов, доверенные устройства, лимит попыток и блокировка после серии неудач;
- пакет **`@better-auth/passkey`** (вынесен из ядра, версия совпадает с ядром) — регистрация и вход по passkey;
- `admin`-плагин — роли, бан, имперсонация;
- сессии с обновлением, `session.mfaVerified`, отзыв всех сессий пользователя;
- встроенная проверка origin/CSRF и rate limit на своих эндпоинтах;
- шифрование секретов TOTP/кодов ключом `BETTER_AUTH_SECRET`.

## 3. Что придётся заплатить

1. **Схема и данные.** Better Auth владеет таблицами `user`, `session`, `account`, `twoFactor`, `passkey`. Наша `accounts` — одновременно бизнес-профиль (роль, аватар, блокировка), на неё ссылаются `orders.user_id_id` и `activity_logs.actor_id_id`. Нужен либо маппинг «`user` = `accounts`» (Better Auth позволяет указать свою модель/поля в Kysely-адаптере), либо отдельная `user` + FK на `accounts`. Без этого поедут заказы и аудит.
2. **Пароли.** По умолчанию Better Auth использует scrypt; при переходе нужно передать свои `hash`/`verify` на bcryptjs, иначе все пользователи идут в сброс пароля.
3. **TOTP-секреты.** У нас они зашифрованы своим ключом (`encryptMfaSecret`, HKDF от `AUTH_SECRET`). При миграции их надо расшифровать и перешифровать в формат Better Auth, иначе все пользователи перенастраивают 2FA.
4. **Passkeys.** Записи WebAuthn (public key, counter, transports) переносимы, но формат credential id и хранение счётчика надо сверить с плагином; в худшем случае passkeys перерегистрируются (у части пользователей).
5. **Сессии и proxy.** Сейчас `proxy.ts` и `requireStaff()` опираются на JWT Auth.js и таблицу `auth_sessions`; при переходе эту связку надо переписать на сессионную проверку Better Auth. Это самый заметный по риску кусок — именно здесь живёт разграничение staff/customer.
6. **Тесты.** Тесты, которые подменяют `@/auth` и `payload-native`, придётся переписать на новую границу (сессия Better Auth), иначе они будут проверять несуществующий контракт.
7. **Зависимость.** Проект движется быстро (1.7.x, плагины выносятся в отдельные пакеты), плюс тянет `kysely`, `jose`, `zod`, `@noble/*`. Для проекта с правилом «минимум зависимостей в security-критичном коде» это осознанный обмен: меньше своего кода, больше чужого.

## 4. Вывод

**Переходить стоит, но не сейчас и не одновременно с удалением Payload.**

Аргументы за переход:
- исчезает наш самый рискованный код — TOTP, ротация refresh-токенов, церемонии WebAuthn (около 800 строк), который мы поддерживаем сами и обязаны сами же аудировать;
- MFA-политика, lockout и доверенные устройства уже реализованы и протестированы сообществом;
- Better Auth официально поддерживает Next 16 и React 19, то есть совместим с нашим стеком;
- libSQL/SQLite поддерживается через Kysely-диалект, отдельная БД не нужна.

Аргументы против немедленного перехода:
- сейчас в работе удаление Payload: меняются и данные, и доступ. Две миграции авторизации одновременно — это двойной риск для входа и для staff-разграничения;
- наша реализация уже закрывает требования (fail-closed MFA, отдельный staff-режим, отзыв сессий, rate limit) и покрыта тестами;
- переезд не бесплатный: миграция хешей, TOTP-секретов и passkey, переписывание proxy/guard-слоя и тестов.

## 5. План, если решаем переходить

1. **Предусловие:** завершить удаление Payload (данные и доступ уже на своём SQL-слое).
2. **Схема:** Kysely + `@libsql/kysely-libsql` на тот же файл; `accounts` остаётся профилем, Better Auth-модель `user` маппится на неё (id совпадает), бизнес-FK не меняются.
3. **Пароли:** собственные `hash`/`verify` на bcryptjs — вход продолжает работать без сброса.
4. **MFA:** миграция `mfa_secret` → twoFactor-таблица с перешифровкой; backup-коды переcоздаются (10 новых, старые инвалидируются — это безопаснее, чем переносить хеши).
5. **Passkeys:** перенос credential id/public key/counter; для непереносимых — письмо «зарегистрируйте passkey заново».
6. **Сессии:** новый `requireStaff`/`proxy` на сессии Better Auth, staff-режим сохраняем как отдельное требование (роль из БД при каждом запросе, как сейчас).
7. **Тесты:** переписать auth-тесты на новую границу, добавить интеграционный тест «staff без MFA не попадает в /admin» и «понижение роли действует сразу».
8. **Раскатка:** сначала обычные пользователи, staff — последними; откат — старая таблица `auth_sessions` остаётся нетронутой до подтверждения.

Оценка работ: 3–5 дней с миграцией данных и тестами, при условии, что Payload уже удалён.
