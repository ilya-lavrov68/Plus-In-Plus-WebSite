# Обязательный комплексный workflow для ИИ-агентов Plus In Plus

## 1. Назначение и главный критерий готовности

Этот документ обязателен для текущего и будущих ИИ-агентов при любой разработке, исправлении, проверке или оптимизации Plus In Plus. Он дополняет `AGENTS.md`, [`docs/ui-ux-pro-max.md`](ui-ux-pro-max.md) и профильные security-документы, а не заменяет их.

**Нельзя считать страницу или функцию готовой только потому, что интерфейс выглядит правильно, компонент рендерится или unit test проходит.** Готовым считается проверенный вертикальный сценарий:

> пользовательское действие → корректный UI → серверная обработка → авторизация → валидация → данные/транзакция → безопасный результат → обновление затронутых представлений → ошибки и восстановление → end-to-end доказательство.

Если часть цепочки действительно отсутствует, например у чисто декоративного SVG нет mutation, это явно обосновывается. Нельзя просто не заметить серверную часть, скрытый API, CMS или проверку роли.

Обещание «сайт отвечает мгновенно» без сопоставимых измерений недопустимо. Для оптимизации дополнительно обязателен [`docs/next-forge-optimization.md`](next-forge-optimization.md).

## 2. Приоритеты и неизменяемые границы

Порядок приоритета:

1. Явные требования пользователя и утверждённые решения PIP.
2. Безопасность, приватность, авторизация и целостность данных.
3. Возможность завершить пользовательский сценарий, включая ошибки и recovery.
4. Доступность, RU/EN, адаптивность и устойчивость author-controlled контента.
5. Производительность, подтверждённая измерениями.
6. Визуальная выразительность и удобство реализации.

До начала работы агент выписывает применимые ограничения. В частности:

- обычный вход клиента и отдельный Admin-mode staff login сохраняются;
- `USER`, `MANAGER`, `ADMIN`, `FOUNDER` не смешиваются; manager получает только разрешённый customer/order scope;
- CMS остаётся database-authoritative; blog, notes, embeds, Markdown import и Canva graphics остаются под контролем автора;
- quote/orderable-service rules и подтверждение цены manager/founder нельзя обходить;
- Robokassa нельзя объявлять работающей без реального подтверждения приёма платежа;
- схема БД не меняется без предупреждения, backup/review и отдельного согласованного плана;
- секреты, пароли, токены, MFA/PII и production-дампы не попадают в код, тесты, логи, скриншоты или PR;
- production остаётся HTTPS-only; security headers, origin/WebAuthn/MFA/session/rate-limit проверки не ослабляются ради теста или скорости;
- существующая функциональность не удаляется ради упрощения diff или уменьшения bundle;
- визуальные PIP-ограничения и запрет emoji-as-icon соблюдаются по `docs/ui-ux-pro-max.md`.

Если задача требует нарушить одно из этих условий, агент останавливается и запрашивает решение пользователя, а не меняет границу молча.

## 3. Обязательная последовательность работы

### Шаг 0. Прочитать правила и установить фактическое состояние

1. Прочитать `AGENTS.md`, этот документ и профильные документы затронутой области.
2. Для любой UI-работы полностью применить `docs/ui-ux-pro-max.md`.
3. Проверить ветку, `git status`, последний commit и незакоммиченные изменения. Не затереть чужую работу.
4. По `package.json`, lockfile и реальным imports установить текущие версии и команды, а не предполагать stack по памяти.
5. Прочитать существующие тесты, CI и env example. Не добавлять новый runner или dependency, если существующий механизм уже решает задачу.

### Шаг 1. Сформулировать контракт сценария

До правки записать кратко:

- кто действует: anonymous, `USER`, staff с конкретной ролью;
- начальное состояние и входные данные;
- observable success: что увидит пользователь и что изменится на сервере;
- запрещённые исходы: чужие данные, неправильная роль, повторная запись, stale UI, потеря введённых данных;
- состояния loading, empty, validation error, server error, unauthorized/forbidden/not found, offline/retry;
- что именно не входит в задачу.

Для bug report сначала описать наблюдение, не диагноз. Например: «фон карточки на 6 px шире контура», а не «сломан весь timeline».

### Шаг 2. Построить карту всей цепочки

Найти код каждой применимой строки до выбора исправления:

| Слой | Что проверить в PIP |
| --- | --- |
| Маршрут | `app/**/page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `not-found.tsx`, route handlers |
| Публичный UI | Server Components, client boundaries, локализация, states, доступность |
| Чтение | `lib/*data*.ts`, профильные `lib/*.ts`, Prisma select/include/filter/order/pagination |
| Авторизация | `proxy.ts`, `auth.ts`, `auth.config.ts`, `lib/admin-session.ts`, ownership и role checks у самой операции |
| Mutation | `app/actions/*.ts`, `app/api/**/route.ts`, client submit/retry/double-submit |
| Вход | `unknown` → Zod/существующие validators, allowlist полей, bounds, content limits, file type/size |
| Запись | Prisma transaction, уникальность, идемпотентность, порядок операций, audit log |
| После записи | `revalidatePath`, `router.refresh`, локальный state, связанные admin/public views |
| Ошибки | Безопасный result/status, sanitized log, понятный следующий шаг пользователю |
| Проверки | Unit/component, HTTP integration, negative authorization, browser E2E, production smoke |
| Документация | README, deployment/security/env/runbooks и этот workflow, если изменился процесс |

`layout` и `page` могут выполняться параллельно. Поэтому guard только в layout или middleware не заменяет авторизацию у data access и mutation.

### Шаг 3. Воспроизвести и сохранить baseline

До изменения:

- повторить дефект через реальный пользовательский путь;
- для UI сделать browser screenshot и измерить геометрию на затронутых widths;
- для API/server action зафиксировать method, route, безопасное тело, status и sanitized response;
- для БД проверить фактический query/transaction path, не выдумывать production execution plan;
- для производительности записать commit, production/dev режим, cold/warm, viewport, сеть, БД/регион и повторяемые метрики;
- отделить существующие ошибки от тех, которые появятся после diff.

Один cropped screenshot, статический JSX или успешный render — это наблюдение, но ещё не полный diagnosis. Если воспроизведение невозможно, прямо указать ограничение и не объявлять причину окончательно доказанной.

### Шаг 4. Выбрать минимальное полное изменение

Исправление должно быть минимальным по архитектурному риску, но полным по сценарию.

- Точечная геометрия не является поводом для редизайна, новой animation library или переписывания CMS.
- UI-заглушка не является завершением отсутствующего server flow.
- Рефакторинг «заодно», миграция БД, major upgrade и оптимизация других страниц выносятся в отдельное согласованное изменение.
- Если для полного сценария действительно нужны несколько файлов, изменяются все они в одном когерентном PR с общими тестами.

### Шаг 5. Реализовать вертикальный сценарий

Применить правила разделов 4–7 этого документа. Не оставлять TODO на критичном пути и не сообщать success, пока сервер не подтвердил результат.

### Шаг 6. Проверить positive, negative и recovery paths

Минимум один успешный путь недостаточен. Проверить применимые запреты:

- anonymous не получает protected данные и не выполняет mutation;
- клиент не читает/изменяет чужой заказ;
- manager не получает admin/founder возможности;
- admin не получает founder-only settings/finance/unlock;
- malformed, oversized и unexpected input отклоняется без побочной записи;
- повторный submit/retry не создаёт недопустимый duplicate;
- ошибка БД/внешнего сервиса не маскируется под success;
- после failed mutation пользователь может исправить ввод и повторить действие;
- после success обновляются все затронутые представления, а не только текущий client state.

### Шаг 7. Выполнить browser и production проверки

UI проверяется в браузере после финального diff. Затронутый сценарий повторяется в production build/start, если это доступно; dev-only HMR, hydration и cache поведение не выдаются за production evidence.

Базовые команды репозитория:

```bash
npm run lint
npx tsc --noEmit
npm test
npm run security:audit
npm run security:dependencies
npm run build
```

Команды запускаются последовательно там, где они используют общие generated artifacts. В частности, не запускать параллельно `tsc` и `next build`, потому что `.next/types` может создать race.

### Шаг 8. Синхронизировать документацию и отчёт

В том же изменении обновить все затронутые документы и явно разделить:

- **подтверждено:** что действительно выполнено и какой командой/сценарием;
- **не проверено:** недоступный browser, staging, внешний сервис, реальный платёж или restore drill;
- **запланировано:** будущие этапы, которых в текущем diff нет;
- **ограничения:** что пользователь/эксплуатация обязан настроить отдельно.

Нельзя переносить результаты старого PR на новый HEAD без повторной проверки.

## 4. Правила серверной и клиентской реализации

### 4.1. Server Components и данные

- Сохранять server-first подход; клиентским делать только компонент, которому нужны browser APIs, события или локальное состояние.
- Не передавать через RSC boundary весь user/order/CMS row: формировать минимальный view model без секретов и лишних полей.
- Использовать существующие `select`, pagination и aggregates. Не загружать полный список ради count или нескольких карточек.
- Независимые reads можно объединять через `Promise.all` только после обязательных guard-шагов. Авторизацию, проверку ownership, зависимые transaction/payment операции нельзя переставлять ради параллелизма.
- Request dedupe и cache не должны переносить данные между пользователями или делать personalized response общим.
- Empty fallback при отсутствии необязательной интеграции допустим только если это осознанный контракт. Ошибка чтения не должна молча выглядеть как «данных нет», если это мешает диагностике или действию пользователя.

### 4.2. Авторизация у операции

Для каждого protected read/write:

1. Проверить наличие настроенной auth-цепочки и актуальной session.
2. Проверить требуемый режим входа и MFA для staff.
3. Получить/сверить текущую роль по существующей `lib/admin-session.ts` policy.
4. Проверить ownership/scope конкретной записи.
5. Только затем читать или изменять защищённые данные.

Middleware остаётся дополнительным perimeter, а не единственной проверкой. Нельзя сначала выполнять Prisma/provider query и лишь потом вызывать `auth()`.

### 4.3. Валидация и сериализация

- Server action и route handler принимают `unknown`, а не доверяют TypeScript-типу из client payload.
- Использовать allowlist полей и существующие Zod/validators; проверять длины, диапазоны, control characters, MIME/signature и размер файлов.
- Не сериализовать произвольные объекты в URL-encoded Auth.js boundary. Для structured assertion/challenge использовать согласованную JSON-сериализацию, bounded parse и отличие `undefined` от строки `"undefined"`.
- Не смешивать WebAuthn, TOTP и backup-code ветки при malformed input.
- Клиентская валидация улучшает UX, но никогда не заменяет серверную.

### 4.4. Запись, transaction и идемпотентность

- Несколько связанных записей, включая audit log, выполнять в существующей transaction-границе.
- Не записывать audit об успехе до фактического успеха основной операции.
- Для webhook, payment, retry и повторного submit предусмотреть уникальность/идемпотентность и корректный replay response.
- Не подменять серверную цену, статус, роль или ownership значениями из клиента.
- Не ослаблять quote/orderable rules и manager/founder price confirmation.
- Внешний вызов не считается частью атомарной БД-транзакции; явно описать компенсацию/retry и состояние при timeout.

### 4.5. Ответ, ошибки и обновление UI

- Использовать типизированный безопасный result либо правильный HTTP status; не возвращать `200` с ложным success при отказе.
- Пользователь получает локализованное объяснение и следующий шаг. Внутренние SQL, секреты, stack, PII и provider payloads ему не раскрываются.
- Логировать только sanitized technical context. Не логировать пароли, TOTP, backup codes, session tokens, полные заказы или персональные данные.
- `revalidatePath` вызывать для фактически затронутых public/admin путей после commit.
- `router.refresh()` и success state применять только после подтверждённого success.
- Pending state защищает от double submission, но не заменяет серверную идемпотентность.
- Optimistic UI допустим только для обратимого действия с понятным rollback. Нельзя оптимистично объявлять вход, MFA, оплату, выдачу роли или необратимую запись успешными.

## 5. Профильные чек-листы

### 5.1. UI-блок, связанный с CMS

Даже для «только CSS» проверить:

- [ ] публичный Server Component получает реальные данные из существующего reader;
- [ ] пустые, malformed и длинные author-controlled значения имеют предусмотренный результат;
- [ ] RU и EN не ломают геометрию;
- [ ] admin reader защищён независимо от layout;
- [ ] соответствующая server action повторно валидирует input и проверяет роль;
- [ ] связанные записи и audit log остаются транзакционными;
- [ ] после сохранения вызываются нужные revalidate/refresh;
- [ ] editor показывает pending, success, error и не теряет ввод при ошибке;
- [ ] browser review повторён после финального fix.

Для timeline дополнительно сохраняются glass, spine, connectors, rounded traces, один native scroll-timeline, one-shot reveal и reduced motion. Structural test не заменяет измерение `article`/SVG/connector в браузере.

### 5.2. Login, MFA, session и account

- [ ] ordinary customer login протестирован отдельно от staff Admin-mode;
- [ ] staff без MFA не получает защищённый staff access;
- [ ] TOTP, passkey и backup-code пути не перехватывают malformed payload друг друга;
- [ ] refresh, rotation, reuse, expiry, logout и закрытие/повторное открытие страницы проверены по сценарию;
- [ ] callback/return URL проходит существующий origin allowlist;
- [ ] реальный Next HTTP flow проверен, а не только отдельная функция сериализации;
- [ ] невалидная session, БД и provider error не выдают клиенту секреты;
- [ ] доступность password manager, paste, autofill, pending/error/recovery не нарушена.

Если внешний отказ не воспроизводится, локальный успех фиксируется именно как локальный, а проблема не объявляется окончательно закрытой на всех окружениях.

### 5.3. Cart, orders, support и оплата

- [ ] anonymous/authenticated flow соответствует утверждённому контракту; `/api/support` остаётся authenticated-only и account-linked;
- [ ] заказ привязан к текущему аккаунту, чужой id не даёт доступа;
- [ ] manager видит только разрешённые customer/order fields;
- [ ] сервер пересчитывает цену и проверяет активность/orderable/остатки;
- [ ] quote и подтверждение цены не заменены клиентским числом;
- [ ] checkout, cancel, invoice и status transitions проверены на допустимые и запрещённые состояния;
- [ ] повторный webhook/retry не создаёт второй платёж/заказ и не откатывает более новое состояние;
- [ ] Robokassa success не объявляется без подтверждённого реального приёма платежа;
- [ ] failure/timeout имеет безопасный recovery и не обнуляет уже оплаченный заказ.

### 5.4. Новый или изменённый API

- [ ] описаны method, route, auth, request schema, response schema и все status codes;
- [ ] применены существующие origin, rate-limit, CSP/security headers и body limits;
- [ ] не поддерживаемые методы и content types обрабатываются предсказуемо;
- [ ] cache policy явно указана; personalized ответ не попадает в shared cache;
- [ ] health check не раскрывает секреты и не выдаёт процессный успех за готовность всех зависимостей;
- [ ] есть positive, negative, malformed и реальный HTTP integration tests.

### 5.5. БД и инфраструктура

- [ ] сначала доказано, что существующей схемы недостаточно;
- [ ] пользователь предупреждён до изменения схемы;
- [ ] подготовлены backup, rollback/expand-contract план, проверка данных и deployment order;
- [ ] локальный SQLite/throwaway файл не выдаётся за staging/Turso/production evidence;
- [ ] индексы, регион, pooling и новый provider обоснованы фактическими запросами и измерениями;
- [ ] секреты не копируются в тестовые файлы и CI-логи.

## 6. Матрица доказательств

Выбирать уровни по риску; для auth/payment/data integrity обязательны наиболее реалистичные доступные проверки.

| Уровень | Что доказывает | Чего не доказывает |
| --- | --- | --- |
| Lint/typecheck | Синтаксис, правила и типы | Runtime, права, визуальную геометрию |
| Unit/component | Чистую логику, контракт разметки, states | Реальный Next serialization, БД, browser layout |
| Prisma/repository integration | Query, constraints, transaction на изолированной БД | Тот же регион/нагрузку/production staging |
| Next HTTP integration | Serialization, cookies, redirects, status, route/action boundary | Полный click flow и визуальное качество |
| Browser E2E | Сценарий, клавиатуру, responsive, console/network, screenshots | Production инфраструктуру без соответствующего окружения |
| Production build/start smoke | Собираемость и базовые реальные маршруты | Все роли, внешние провайдеры и нагрузку |
| Staging/field measurement | Интеграции и показатели конкретного окружения | Автоматическую корректность будущих изменений |

Обязательные правила доказательств:

- тестовые fixtures и throwaway БД изолированы от production и не вставляются как данные в прикладной UI;
- существующие mocks не подменяют тестируемую границу: если сломался Auth.js serialization, нужен реальный Auth.js/Next boundary;
- regression test должен падать на старом дефектном поведении или это ограничение честно объясняется;
- случайный success одного прогона не заменяет повторяемый сценарий;
- скриншоты не содержат PII, секреты или закрытые production-данные;
- при невозможности проверки пишется «не проверено», а не предполагается успех.

## 7. Правила оптимизации

До любой оптимизации прочитать `docs/next-forge-optimization.md` и выполнить короткий цикл:

1. **Измерить:** определить узкий сценарий и baseline.
2. **Локализовать:** browser, JS, rendering, middleware, server waterfall, Prisma, сеть или внешний provider.
3. **Сформулировать гипотезу:** какой механизм и какую метрику изменит diff.
4. **Изменить одну группу причин:** не смешивать cache, schema, UI и major upgrades без необходимости.
5. **Проверить корректность:** auth, roles, freshness, mutations, errors, RU/EN и browser flows остаются зелёными.
6. **Сравнить честно:** тот же режим, данные, cold/warm класс и условия; несколько прогонов вместо одного лучшего числа.
7. **Зафиксировать:** метрики до/после, накладные расходы, rollback и непроверенные окружения.

Нельзя удалять функциональность, отключать безопасность, скрывать ошибки или переводить всё в client cache ради улучшения цифры.

## 8. Финальный чек-лист агента

Перед сообщением о готовности ответить по пунктам:

- [ ] затронутый сценарий описан end-to-end, а не только визуально;
- [ ] причина и baseline отделены от предположений;
- [ ] diff минимален и не содержит несогласованной архитектурной миграции;
- [ ] server guards находятся у операции, ownership/roles проверены negative tests;
- [ ] validation, transaction, errors, revalidation и client recovery завершены;
- [ ] существующая функциональность и утверждённые PIP-решения сохранены;
- [ ] RU/EN, responsive, keyboard, reduced motion и console/network проверены по применимости;
- [ ] regression проверяет именно исправленный дефект;
- [ ] полные тесты, lint, types, security audit и production build выполнены на финальном diff;
- [ ] production smoke/browser evidence получен либо ограничение явно названо;
- [ ] нет секретов, PII, случайных artifacts и тестовых production-данных в diff;
- [ ] документация синхронизирована, планы не выданы за выполненную работу;
- [ ] в отчёте есть фактические команды/результаты и честные оставшиеся риски.

## 9. Шаблон итогового отчёта

```text
Что изменено
- Конкретный сценарий и файлы.

Почему
- Наблюдённая причина, а не общий редизайн.

Проверено
- Команды и число тестов.
- Browser/production сценарии, widths, роли и negative paths.
- Метрики до/после, если задача была об оптимизации.

Ограничения
- Что не проверено и почему.
- Какие внешние условия остаются на пользователе/эксплуатации.

Не входило в изменение
- Будущие оптимизации, миграции и интеграции, которые только запланированы.
```
